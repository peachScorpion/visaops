这是**技术层需求文档**，写给三类人看：

## 0.2 系统定位与业务边界

VisaOps 把众信的签证业务从"全人工"搬进系统，覆盖**从供应商上品到客户拿到签证结果**的完整链路。

### 业务模型：自营 + 供应商双轨

- **产品来源**：产品由**供应商在 UBK 自行录入并报价**，平台目录随之自动登记。平台侧（OPS）
  只管**材料标准**（签证表模板 / 材料样例 / 国家送签材料库）与**审核放行**，不建产品、不定价。
- **履约主体**：签证办理中心以**供应商（UBK）为主力**，众信侧（UOM）看整体节奏并协助操作。
  > 唐美芳 2026-09-08：「签证办理中心现在主要就是 UBK 干活，UOM 只是查看整体节奏和协助操作。」
- **双通道销售**：B 端（CSP 门店 / 同业）与 C 端（客户小程序）**分别审核、分别上架**。
  供应商上品默认上架 B 端；勾选「上架 C 端」才会同时出现在客户小程序。
  > 唐美芳 2026-09-09：「B 只审核 B 的，C 只审核 C 的，2 拨人处理，所以千万不要混在一起。」

### 硬约束：五项动作永久保留人工

各国官方签证系统（CEAC / VFS Global / TLScontact / ustraveldocs）**均无公开 API、且不授权第三方抓取**。
以下五项对外**不得承诺自动化**，系统只做辅助（预填、提醒、留痕），不做代操作：

| # | 动作 | 系统能做的 | 系统不做的 |
|---|---|---|---|
| 1 | 官方申请表提交 | 结构化收集答案、生成可复制的填报清单 | 自动登录官网提交 |
| 2 | 签证费缴纳 | 记录缴费金额与回执号 | 代客在官网付款 |
| 3 | 面签号抢占 | 记录预约号与时间地点、到期提醒 | 自动刷号 |
| 4 | 材料递交 | 记录送签批次与递交方式 | 代替线下递交 |
| 5 | 生物信息采集（指纹） | 提示需采集、记录采集点 | 任何形式的代办 |

### 本期不做

- **分销分润与返佣**（唐美芳明确口径：本期不涉及）；
- 原件寄回给客户由**签证中心 / 银行直接寄回客户本人**，不经供应商，因此**无「资料返还」履约环节**。
  > 唐美芳 2026-09-09：「一般原件寄回不需要经过供应商，签证中心会通过银行或者直接寄回的方式，所以寄回功能不需要。」

## 0.3 五套端 · 八种身份

系统由**五套相互独立的端**组成。角色是端内的身份，不是并列的入口——同一个人换端不换账号。

| 端 | 形态 | 使用者 | 职责 |
|---|---|---|---|
| **客户端** | H5 / 小程序 | 直客、散客本人 | 自助选签证、下单付款、上传材料、查进度、查结果 |
| **CSP 门店工作台** | PC | 门店销售、同业代理 | 接待客户、比价选品、代客下单、跟进办理、发起退款 |
| **有米小程序** | 移动端 | 门店销售（手机） | CSP 的移动端，同账号同数据。当面查产品、代客下单、把填表链接直接发给客人 |
| **UOM 运营平台** | PC | 平台管理员 / 专员 / 主管 / 财务 | 一套系统四种身份：材料标准配置、工单协助、派单与审批、收款与结算 |
| **UBK 供应商门户** | PC | 优耐德、竹园等资源方 | 维护收料地址、录产品与报价、选上架范围、接单履约、结算对账 |

### 八种身份

| role | 名称 | 所属端 | 演示账号 | 职责边界 |
|---|---|---|---|---|
| `customer` | 客户 | 客户端 | c1 / c2 | 只能看自己的订单与办签人 |
| `csp` | 门店销售 / 同业 | CSP | sales / agent | 只能看本门店（org）的订单 |
| `youmi` | 门店销售（移动端） | 有米 | sales | 同 `csp`，仅终端不同，不是独立角色 |
| `uom` | 签证操作专员 | UOM | op1 / op2 | 工单履约与协助；不碰产品与钱 |
| `lead` | 签证主管 | UOM | lead | 派单改派、退款审批、拒签归因 |
| `fin` | 财务 | UOM | fin | 收款到账确认（放行 gate）、结算、退款出账 |
| `ops` | 平台管理员 | UOM | ops | **UOM 内部超级管理员**，含 uom/lead/fin 全部权限；主职是材料标准与产品审核。边界止于 UOM 内部，不越界到 CSP / UBK / 客户端 |
| `ubk` | 供应商 | UBK | sup / sup2 / sup_a / sup_b | 只能看本供应商（org）的产品、订单、工单 |

演示环境密码统一 `888888`。

### 数据边界（越权判定规则）

| 身份 | 可见数据范围 | 实现约定 |
|---|---|---|
| `customer` | `ord.buyer_user = 自己` | 接口层按 user id 过滤 |
| `csp` / `youmi` | `ord.org_id = 自己所属门店` | 接口层按 org 过滤 |
| `ubk` | `wo.sup_org = 自己所属供应商` | `sup_wo_guard()` 统一校验工单归属 + 收款放行 |
| `uom` / `lead` | 全量工单（跨供应商） | 只读为主，可协助操作 |
| `fin` | 全量资金单据 | 不可见客户联系方式明文 |
| `ops` | UOM 全量 | 不含 CSP / UBK / 客户端的独有页面 |

> **供应商不下发客户姓名与手机号**：UBK 工单上办签人显示为脱敏姓名，联系方式不下发，
> 需要联系客户时由 UOM 专员或门店销售转达。

## 0.4 核心对象与引用链

理解这两条链，系统的大部分"为什么这里查不到数据"就能自己回答。

### 链一：材料标准（配置侧，自上而下）

```
国家签证表模板 formver   ← 底层字典，一个国家一套官方表（如 日本 · 签证申请书）
        ↑ formver_id
国家送签材料库 fullver   ← 某国某签证类型的完整送签清单，一个版本一份
        ↑ fullver_id       （含 fullver_item：逐项材料，分人群、分提供方式）
       产品 product / 供应商产品 sup_product
```

**关键规则（2026-09-09 修正）：**

1. **表模板是底层字典，可被多份材料清单反复引用**，因此它**只有「启用 / 禁用」两个状态，
   没有发布状态**。国家送签材料库**只能引用处于启用状态的表模板**。
   > 唐美芳原话：「这个模板是底层，可以被国家送签材料库多次引用，所以国家签证表模板只需要有启用、禁用……
   > 你现在加上了发布未发布状态整复杂了，退回下。」
2. **工单要填哪张官方申请表，沿引用链取，不按国家猜**：
   `订单 → 供应商产品（优先）/ 平台产品 → fullver_id → fullver.formver_id → formver`。
   任一环断裂，工单上的「填申请表」按钮置灰并提示断在哪一环，不再报笼统的"模板不存在"。
3. **材料项数对不上是正常的，两者口径不同**：
   - **国家送签材料库的项数** = 该国送签要交的**全部材料**（含护照、照片、在职证明、银行流水…），
     其中一部分由客户提供，一部分是我方凭证；
   - **国家签证表模板的项数** = 官方申请表上的**题目数**（客户必填题 / 选填题）。
   一个是"要交几样东西"，一个是"表上要答几道题"，不应相等。

### 链二：交易与履约（运行侧，自左而右）

```
订单 ord ──┬── 办签人 applicant（一单多人）──── 工单 wo（一人一单，1:1）
           │        ├── 材料 mat（逐项，可驳回）
           │        └── 官方申请表任务 form_task ── 答案 form_answer
           ├── 收款 pay / 应付 payable / 退款 refund
           └── gate（财务收款放行开关：0 未放行 / 1 已放行）
```

**关键规则：**

1. **一个办签人一张工单**（`wo.applicant_id` 唯一），工单号 `VW-` 开头，全局唯一可搜。
   订单号 `VS-` 开头。同一订单多人，就是多张工单，可分派给不同经办人。
2. **收款放行 gate 是履约的总闸**：`ord.gate = 0` 时供应商看不到工单、任何履约动作被拒。
   财务在收款管理确认到账后置 `gate = 1`。
   > 唐美芳 2026-09-08：「必须财务点确认到账后才能开始干活。」
3. **办签人资料必须在支付前录齐**：下单后 24 小时内未录齐 → 订单自动取消（`ord.info_deadline`）。
4. **订单状态只管钱走到哪**（5 个值），办理进展是**由办签人进度聚合出来的派生值**，不落在订单状态上。

## 0.5 状态机总表

系统里所有状态码集中在这一节。**任何页面上出现的状态文字，都必须来自下表，不得就地另起名字。**

### 0.5.1 订单状态 `ord.status`

| 码 | 展示名 | 含义 | 可迁移到 |
|---|---|---|---|
| `created` | 待付款 | 已下单未支付 | `paid` · `cancelled` |
| `paid` | 已付款 | 款已收；办理进展另算 | `done` · `refunded` |
| `done` | 已完成 | 全部办签人已出结果 | `refunded`（拒签退） |
| `cancelled` | 已取消 | 超时未付 / 主动取消（终态） | — |
| `refunded` | 已退款 | 退款出账完成（终态） | — |

> **「办理中」不是订单状态**。它由办签人进度算出（`work_status()`），只作展示。
> 唐美芳 2026-08-31：「订单状态里很少有办理中这种中间态的，先去掉吧。」

### 0.5.2 收款放行 `ord.gate`

| 值 | 含义 | 谁改 | 影响 |
|---|---|---|---|
| `0` | 未放行 | 初始值 | 供应商看不到该单工单；填表 / 审材料 / 预约 / 登记结果全部拒绝 |
| `1` | 已放行 | 财务在「收款管理」确认到账 | 工单下发供应商，履约动作解锁 |

### 0.5.3 办签人办理进展 `applicant.progress`（六步）

| 码 | 展示名 | 进入条件 | 通用档 |
|---|---|---|---|
| `P1` | 待收料 | 工单创建（gate=1 后可操作） | G1 |
| `P2` | 待审核 | 客户 / 销售提交材料后 | G1 |
| `P3` | 待提交至官网 | 材料全部审核通过 | G2 |
| `P4` | 待预约 | 官方申请表填报完成 | G2 |
| `P5` | 待出结果 | 已递交使领馆 / 已面签 | G2 |
| `P6` | 已完成 | 签证结果已登记 | G3 |

**通用三档 `GSTAGE`**（给不看细节的人用的粗粒度视图）：

| 码 | 展示名 | 覆盖 | 从该档进入时落到 |
|---|---|---|---|
| `G1` | 待收料 | P1 · P2 | P1 |
| `G2` | 处理中 | P3 · P4 · P5 | P3 |
| `G3` | 已出结果 | P6 | P6 |

> **P5 为什么叫「待出结果」不叫「待出签」**：需面签的产品客人本人到馆，材料不经我方的手，
> 没有"送签"这个动作，叫「待出签」会让人以为还要我方递交。
> 唐美芳 2026-09-03：「待出签状态，不需要送签了，现在签证中心都是线上办理了。」

**旧十步 → 新六步迁移表** `PROG_MIGRATE`：
`P1→P1 · P2→P2 · P3→P3 · P4→P3 · P5→P4 · P6→P5 · P7→P5 · P8→P5 · P9→P6 · P10→P6`

### 0.5.4 办签人业务状态 `applicant.state`

| 码 | 展示名 | 含义 |
|---|---|---|
| `normal` | 正常 | 在办 |
| `cancelled` | 已取消 | 随订单取消 |
| `refunded` | 已退款 | 该人已退款出账 |

### 0.5.5 材料状态 `mat.status`

| 码 | 展示名 | 谁改 | 说明 |
|---|---|---|---|
| `wait` | 待提交 | 初始 | 客户 / 销售尚未上传 |
| `review` | 待审核 | 客户提交后自动置位 | 等待供应商 / 专员审核 |
| `pass` | 已通过 | 供应商 / 专员 | 计入"已通过"数 |
| `reject` | 已驳回 | 供应商 / 专员，**必须填原因** | 客户端标红并提示重传 |

> **注意历史数据里同时存在 `reject` 与 `rejected` 两种写法**，判断逻辑一律按
> `status in ('wait','reject','rejected')` 视为"尚缺"，新写入统一用 `reject`。

**材料数量口径（列表上的三行数字必须互相对得上）：**

- `尚缺 N 项` = 客户必交材料中状态为 `wait / reject` 的条数；
- `客户必交 X / Y 已通过` = Y 是客户必交总数，X 是其中 `pass` 的条数，**X + 尚缺 = Y**；
- `另有建议 M 项 · 我方凭证 K 项` = 不计入必交口径的两类，单列一行，不参与上面的加减。

### 0.5.6 产品审核状态 `sup_product.review_b` / `review_c`

两端各一份，**互不影响**。

| 码 | 展示名 | 含义 |
|---|---|---|
| `none` | 未提交 | 供应商尚未选择上架该端 |
| `pending` | 待审核 | 已提交，等运营审 |
| `approved` | 已通过 | 该端可售 |
| `rejected` | 已驳回 | 带驳回原因回到供应商 |

**是否在售** = `review_x = approved` **且** 该端上架开关为开 **且** 未停售（`off_sale = 0`）。
改价或改材料清单会**自动下架并重新送审**。

### 0.5.7 签证结果 `applicant.visa_result`

| 码 | 展示名 | 联动字段 |
|---|---|---|
| `pass` | 出签 | 签证号、有效期至、停留天数 |
| `reject` | 拒签 | 拒签原因（必填）、拒签分类、责任判定 |
| `withdraw` | 撤签 | 撤签说明 |
| `ap` | 行政审查 | 行政审查截止日 `ap_due` |

> **登记签证结果的表单按结果动态显示字段**：选「出签」才出现签证号 / 有效期，
> 选「拒签」才出现拒签原因与分类，选「行政审查」才出现截止日。不相关的字段不显示、不校验。

**拒签分类 `REJECT_CATE`**：移民倾向 · 材料不实 · 资金约束不足 · 行程不合理 · 面签表现 · 过往拒签史 · 使领馆未说明

**责任判定 `LIABILITY`**：`company` 我司责任 · `customer` 客户责任 · `official` 使领馆/第三方 · `none` 未判定

### 0.5.8 收付款状态

| 字段 | 码 | 客户/门店视角 | 供应商视角 |
|---|---|---|---|
| 支付 | `unpaid` | 待支付 | 待收款 |
| 支付 | `part` | 部分支付 | 部分收款 |
| 支付 | `paid` | 已支付 | 已收全款 |

同一个状态码，两端各用一套措辞，不新增状态位。

### 0.5.9 其他值域

## 0.6 通用交互与文案约定

**这一节是全站规则。第 1–4 册只写各页面的差异，不重复这里的内容。**

### 0.6.1 页面骨架

| 位置 | 放什么 | 不放什么 |
|---|---|---|
| 页面右上角 | **通用操作**：返回、改派、导出、刷新 | 与某条记录相关的操作 |
| 模块内 | **该模块的主操作**（如"申请人材料清单"模块里放审核、填表） | 通用操作 |
| 列表行尾「操作」列 | 该行记录的操作，超过 3 个收进「更多」 | 批量操作 |
| 列表顶部 | 页签（状态分组）→ 筛选条 → 搜索框 → 右侧图标操作 | — |

**工单详情页模块顺序（固定）**：
`① 办理进展 → ② 工单基础信息 → ③ 申请人材料清单 → ④ 操作日志`，通用按钮在右上角。

### 0.6.2 按钮规则

1. **不可用要给理由**：按钮置灰时必须有 title 或行内提示说明为什么（如"未收款放行"、"材料清单未绑定"），
   不允许出现点不动又没有任何解释的按钮。
2. **不可逆操作二次确认**：审核通过 / 驳回、停售、取消订单、退款出账必须弹确认框，
   确认文案要说清**影响面**（如"通过后本产品即在客户小程序展示并可被下单"）。
3. **驳回必须填原因**，原因**原样下发给被驳回方**（供应商 / 客户），不允许只写"不合格"。
4. **同一模块的操作按钮排在一起**，不分散在多个区块。

### 0.6.3 文案约定

| 场合 | 用词 | 不用 |
|---|---|---|
| 后台端（UOM / UBK / CSP） | 客户 | 客人 |
| 后台端 | 办签人、申请人 | 客人、游客 |
| 后台端 | 办结截止日 | 办理时限、SLA |
| 客户端 | 你 / 你的 | 您（保持轻量口吻）、用户 |
| 全站 | 国家送签材料库 | 材料清单库、完整版库 |
| 全站 | 国家签证表模板 | 表单模板、申请表模板 |

- **后台页面不放「操作说明」块**。
  > 唐美芳 2026-09-09：「后台所有页面的操作说明去掉吧，感觉逻辑更新了文案也没同步更新。」
  页面说明改为标题旁的 `i` 悬浮提示，随代码一起改，不再单独维护一段长文。
- **列表标题与左侧菜单名一致**，同一个页面不允许两处叫两个名字。
- **金额一律 `¥` + 千分位**，区间用 `最低 / 最高` **换行**展示，不写在一行里。
- **时间**：列表用 `YYYY-MM-DD HH:mm`，详情用 `YYYY-MM-DD HH:mm:ss`；相对时间只在"最近操作"处使用。

### 0.6.4 列表通用要求

1. **每条记录都要有可搜索的唯一编号**（订单 `VS-`、工单 `VW-`、产品编号），并可直接粘进搜索框定位。
2. **两端同一张列表字段必须对齐**：UOM 的办理中心 = UBK 的办理中心 + 「供应商」「当前办理人」两列。
   > 唐美芳 2026-09-08：「我看现在 UOM 和 UBK 的列表字段还是对不齐的，请你整合。」
3. **订单、产品、申请人材料各占独立列**，不合并成一格。
4. **空态要说清下一步**（"暂无待审核产品，供应商提交后会出现在这里"），不只写"暂无数据"。
