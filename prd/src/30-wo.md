# 第 3 册 · 签证办理中心

> 本册覆盖工单从生成到出结果的全链路，涉及 UBK 与 UOM 两端。
> 全局状态码、通用交互规则见第 0 册，本册不重复。

## 3.1 范围与两端分工

**签证办理中心是整套系统的履约核心。** 一位办签人 = 一张签证工单（`VW-` 单号），
工单在**财务确认收款到账**后生成并派发。

| | UBK 供应商门户 | UOM 运营平台 |
|---|---|---|
| 菜单名 | 签证办理中心 | 国家签证办理中心 |
| 路由 | `#ubk:board` | `#uom:board` / `#lead:board` / `#ops:board` |
| 角色定位 | **实际干活的人** | **看整体节奏 + 协助操作** |
| 进度粒度 | 三档：待收料 / 处理中 / 已出结果 | 三档为主，六步节点在「办理状态」列里显示 |
| 可见范围 | 仅派发至本供应商（`wo.sup_org`）且已放行的工单 | 专员看自己名下，主管 / 平台管理员看全部 |
| 列表按钮 | 查看详情 · 填申请表 · 提交至官网 · 预约面签 · 登记签证结果 · 改派 | **只有** 查看详情 · 登记签证结果 |

> 唐美芳 2026-09-08：「签证办理中心现在主要就是 UBK 干活，UOM 只是查看整体节奏和协助操作，
> 所以主要以 UBK 为主……只不过 UOM 里多供应商和当前办理人字段，其余操作和内容尽量保持一致。」
>
> 唐美芳 2026-09-09：「UOM 要不只放查看详情和签证结果登记这 2 个按钮好了。」

**为什么供应商侧只有三档**：供应商手上国家五花八门，日本递纸质、韩国走代传，
根本没有「提交至官网」这一步。逼他们逐个节点点，结果是没人点，系统里的进度全是假的。
**底层仍写六步**——`set_progress()` 在跳跃时自动补齐中间环节，轨迹不丢。

## 3.2 工单的生成与派发

### 3.2.1 生成时机（这是最容易被问"为什么办理中心是空的"的一条）

```
客户下单 → 支付 → 财务在「收款管理」核对水单 → 点「确认到账」
        → ord.gate = 1
        → 系统为该订单每位办签人各开一张工单（open_wo）
        → 工单出现在 UOM 办理中心，同时派发至供应商 UBK
```

**支付成功 ≠ 工单生成。** 中间必须有财务点一下「确认到账」。

> 唐美芳 2026-09-08：「必须财务点确认到账后才能开始干活。」

### 3.2.2 生成规则

| 项 | 规则 |
|---|---|
| 工单号 | `VW-` + 序列号，全局唯一，两端列表均可搜 |
| 一单多人 | 一位办签人一张工单，`wo.applicant_id` 唯一 |
| 承办专员 `owner_user` | 按 `uom` 角色账号轮转分配（`ops[i % len(ops)]`） |
| 供应商 `sup_org` | 取该订单所选供应商产品的所属组织 |
| **办结截止日 `sla_due`** | 建单时间 + **套餐承诺办理时长 `pkg.lead_days`**（无套餐时默认 15 天） |
| 供应商经办人 `sup_owner` | 建单时为空，由供应商自行「改派」指派 |
| 初始进展 | `P1 待收料` |

> **「办理时限」已改名「办结截止日」**（唐美芳 2026-09-08：「办理时限的意思是截止日期么，
> 字段名称最好写清楚，让人明白」）。全站不再出现「SLA」「办理时限」字样。

### 3.2.3 未放行工单的提示（必须有，否则两端都以为系统坏了）

| 端 | 提示 |
|---|---|
| UBK | 「另有 **N** 位办签人所在的订单**客户已付款、平台财务尚未确认到账**，按现行规则暂不派发至贵司，财务确认后自动出现在本页，无须联系平台。」 |
| UOM（有工单时） | 「另有 **N** 张已付款订单在等财务确认收款到账，确认后才会为每位办签人生成工单。」+（财务/管理员可见）「去收款管理确认 ›」 |
| UOM（无工单时） | 大段空态：说明工单是财务确认到账那一刻才生成的，并给出财务的操作路径 |

**接口层同样拦截**：`sup_wo_guard()` 校验工单归属 + gate，未放行时返回
`403 该工单尚未派发至贵司（平台财务确认收款到账后自动派发）`。
界面挡住、接口也要挡住——2026-09-09 走查发现过界面挡住、接口没挡的漏洞。

## 3.3 UBK · 签证办理中心（列表）

**路由** `#ubk:board` ｜ **接口** `/api/sup/orders` ｜ **进入角色** `ubk`

### 3.3.1 页签

| 顺序 | 页签 | 过滤条件 |
|---|---|---|
| 1 | 全部 | 全部工单 |
| 2 | **待收料**（默认停在这档） | `stage = G1` |
| 3 | 处理中 | `stage = G2` |
| 4 | 已出结果 | `stage = G3` |

> **「全部」必须排第一**（唐美芳 2026-09-04：「全部 tab 页签在最前面，你怎么每次都把全部
> 放到最后面，不太友好」）。全站已统一为这个顺序。
> **默认落在「待收料」**——那才是要动手的那一档。

### 3.3.2 筛选与排序

**筛选项**：办签人（模糊）· 工单号（模糊）· 订单号（模糊）· 国家（下拉）· 产品（下拉）· 是否超期（已超期 / 未超期）

**排序**：办结截止日（默认升序）· 办理状态

> **超期做筛选项不做页签**：超期是「该办没办」，跟办到哪一步是两回事，
> 一张待收料的工单也可能超期。做成页签会和状态页签互相打架。

### 3.3.3 列表字段（14 列）

| # | 列 | 内容 | 副行小字 |
|---|---|---|---|
| 1 | 工单号 | `VW-…`（等宽字体） | — |
| 2 | 办签人 | 姓名 | 适用人群 |
| 3 | 国家 / 送签地 | 国旗 + 国家 | 送签地 |
| 4 | 签证类型 | 签证类别标签 | 具体签证类型 |
| 5 | 订单号 | `VS-…`（等宽字体） | — |
| 6 | 签证产品 | 产品名 | 套餐名 |
| 7 | **申请人材料** | 「尚缺 N 项」/「已交齐」标签 | ①客户必交 X / Y 已通过（+驳回数）②另有建议 M 项 · 我方凭证 K 项 |
| 8 | 办理状态 | 三档标签 | 面签时间地点 / 「已提交官网」 |
| 9 | 签证结果 | 出签绿 / 拒签红 / 撤签灰 / 行政审查黄 | — |
| 10 | 办结截止日 | 日期；超期时前置红色「已超期」标签 | — |
| 11 | 当前办理人 | 供应商经办人，未指派时显示「未指派」 | — |
| 12 | 创建 | 时间 | 创建人 |
| 13 | 最近操作 | 时间 / 「未再变更」 | 操作人 |
| 14 | 操作 | 见下 | — |

> **国家、签证类型这些关键字段必须独立成列**，不能塞进小字
> （唐美芳 2026-09-08：「比如国家，签证类型，这些都是非常关键的字段，你现在把这些都隐藏了」）。
> **订单、产品、申请人材料各占独立列**，不合并（唐美芳 2026-09-09）。

### 3.3.4 材料列的数字口径（这一格出过账对不上的问题，单列一节）

```
主标签    尚缺 N 项  /  已交齐        N = 客户必交里状态为 wait / reject 的条数
第一行小字 客户必交 X / Y 已通过       Y = 客户必交总数，X = 其中已通过
                                     ⚠️ 必须满足 X + N = Y
第二行小字 另有建议 M 项 · 我方凭证 K 项  这两类不参与上面的加减
```

**三类材料的区别**（这是数字对不上的根源）：

| 类别 | 判定 | 谁提供 | 计不计入"还差 N 项" |
|---|---|---|---|
| **客户必交** | `necessity=must` 且 `by_us=0` | 客户手上现在就有（护照、身份证、在职证明、流水） | ✅ 计入 |
| **我方凭证** | `by_us=1` | 我方办出来才有（申请表确认页、面签预约单、签证费收据） | ❌ 不计入——待收料阶段客户手上根本没有，催也交不出来 |
| **建议材料** | `necessity=suggest` | 客户（房产车产、行程单、邀请函） | ❌ 不计入——不交也能送签 |

**「材料齐备」判定** `st.ready` = **仅看客户必交项**是否全部 `pass`。
把我方凭证算进去，客户材料交齐了进度也永远推不到 P3。

> 唐美芳 2026-09-09：「尚缺 6 项与已通过里的 0/10 还是对不上啊，你怎么总漏掉呢。」
> 起因是主标签数的是"客户必交里没交的"，而"已通过 X/Y"的 Y 是全部材料（含建议项与我方凭证）。
> 现在主线只讲客户必交这一档，另两类单列一行。**UBK 与 UOM 两端共用 `ubkMatCell()`，口径必然一致。**

### 3.3.5 操作按钮矩阵

| 档位 | 按钮（从左到右） |
|---|---|
| **待收料 G1** | 查看详情 · 填申请表（仅当该国有可用表模板）· 登记签证结果 · 改派 |
| **处理中 G2** | 查看详情 · 提交至官网 / 受理号已回填 · 预约面签 / 面签改期 · 登记签证结果 · 改派 |
| **已出结果 G3** | 查看详情 |

**按钮规则：**

1. **「填申请表」只在待收料档出现**。到了处理中，申请表按定义已经填完，
   再摆一个填表按钮只会让人以为还没填完。要改仍可从详情页进。
2. **「填申请表」按钮上带剩余题数**：`填申请表 · 剩 N 题`。
3. **该国没有在线申请表时不显示这个按钮**（`form_avail = false`），
   页面顶部说明里交代原因：「部分国家（如日本）向使领馆递交的是纸质申请表，
   系统内没有在线申请表这一层，此类工单不显示「填申请表」，按贵司既有流程线下填写即可；
   材料清单不受影响。」
4. **「提交至官网」在已回填后变成「受理号已回填」并去掉主色**，仍可点开修改。
5. **「预约面签」在已登记后变成「面签改期」**。
6. **「登记签证结果」从待收料档就能点**——这是刻意的：中间节点由 `set_progress()` 自动补齐，
   不让供应商为了填结果先走完流程。
   > 唐美芳 2026-09-04：「里面的流程节点弄成通用的，可以让他们直接跳过中间流程，
   > 直接标记最后是否出签，怕他们觉得标记系统太过麻烦，增加他们的工作量。」
7. **已出结果的工单不再提供任何操作**，如需更正联系众信。

### 3.3.6 已撤销的按钮（不要再加回来）

| 按钮 | 撤销时间 | 原因 |
|---|---|---|
| **开始处理** | 2026-09-09 | 材料审核已下放给供应商，必交项逐条点「通过」后系统自动转「处理中」。再摆一个手动按钮等于留了一条**不收料也能标处理中**的旁路。<br>唐美芳：「待收料为什么会有开始处理按钮？起个什么逻辑作用？」 |
| **回填缴费** | 2026-09-09 | 缴费不是状态节点，只是取号的前置条件之一，由办理人自己掌握。<br>唐美芳：「缴费回填这个功能可以去掉，毕竟给大使馆是否缴费不影响状态流转。」<br>**字段与历史记录保留**，接口 `/fee/save` 仍在，无界面入口 |
| **提醒客人补交材料** | 2026-09-08 | 唐美芳：「提醒客人补交材料，去掉这个功能，包括 C 端也去掉。」接口 `/sup/urge` 已删除 |
| **挂起工单** | 2026-09-09 | 全库 423 张工单没有一张用过这个状态。真遇到暂缓办理，走订单侧的取消 / 退款更说得清。筛选区的「已挂起」选项一并撤 |

## 3.4 UOM · 国家签证办理中心（列表）

**路由** `#uom:board` / `#lead:board` / `#ops:board` ｜ **接口** `/api/wo/list?scope=…`

### 3.4.1 与 UBK 的差异（只有这四处）

1. **多两列**：供应商 · 当前办理人（众信承办专员，副行显示供应商经办人）
2. **多「创建 / 最近操作」审计列**（UBK 侧 2026-09-09 才补齐，现已一致）
3. **办理状态列多一行小字**：显示六步中的具体节点（如「待提交至官网」），
   以及「补料中」标记
4. **列表只有两个按钮**：查看详情 · 登记签证结果

**页签与 UBK 完全一致**（全部 / 待收料 / 处理中 / 已出结果），默认停在「全部」。

> **六步没有丢**，只是从页签降级为筛选项「当前节点」。原来这里是六个页签，
> 跟供应商那边对不上，两边的人在电话里说的不是同一个词。

### 3.4.2 数据范围（由角色直接决定，不给切换按钮）

| 角色 | scope | 看到 |
|---|---|---|
| `uom` 专员 | `mine` | 自己名下的工单 |
| `lead` 主管 / `ops` 管理员 | `all` | 全部工单 |

> 唐美芳 2026-09-09：「不用区分我的工单和全部工单了，这个用数据权限做到就可以。」
> 原来那两颗按钮还把选择存进 sessionStorage，换个浏览器 tab 看到的范围就不一样。

### 3.4.3 筛选项（11 项，比 UBK 多 5 项）

办签人 · 工单号 · 订单号 · **当前节点**（六步）· 国家/目的地 · **洲** · 签证类型 ·
签证产品 · **适用人群** · **承办专员** · **供应商** · 异常标记

**异常标记**：已超过办结截止日 / 补料未回 / 无异常

### 3.4.4 顶部 KPI 卡（8 格，点击即筛选）

在办工单 · 待收材料 · 待我审材料 · 待提交至官网 · 待预约 · 待出结果 · 补料未回（橙）· 已超期（红）

点击 KPI 卡的效果是**往查询卡里塞筛选条件**，不是跳页签——筛选条件写在查询卡里，看得见也改得掉。

### 3.4.5 已撤销的区块

| 区块 | 原因 |
|---|---|
| **专员负载条** | 「按承办专员筛」这件事查询区的下拉本来就能做，两个入口做同一件事，页面还长了一截 |
| **操作说明** | 作业规范不该常驻在工作台顶部，它属于培训材料 |
| **送签批次 / 资料返还两个页签** | 需面签的产品客人本人到馆、护照由使领馆或银行直接寄回，这两步不存在。**页面与路由都保留**（`#uom:batch` / `#uom:deliver`），日本这类必须由指定代办机构递交的国家仍要用，解开一行注释即可恢复 |

## 3.5 工单详情页（两端共用）

**路由** `#ubk:wo/<工单号>` = `#uom:wo/…` = `#lead:wo/…` = `#ops:wo/…` ｜ **接口** `/api/wo/detail?no=`

### 3.5.1 模块顺序（固定，不得调整）

```
页头（工单号 · 办签人 | 产品 · 套餐 · 订单号 · 办结截止日）   右上角：改派 · 返回签证办理中心
①  办理进展        进展条（4 段）+ 一句「此刻要做的」
②  工单基础信息    16 格 KV
③  申请人材料清单  官方申请表入口 + 材料逐项表
④  操作日志
```

> 唐美芳 2026-09-08：「调整成办理进展模块、工单基础信息模块、申请人材料清单模块
> （相关操作主按钮放在这个模块里）、官方申请表我觉得在申请人材料清单里放个入口就可以了、
> 操作日志模块，通用操作按钮放在页面右上角。」

**右上角只放通用操作**（改派 · 返回）。办理动作跟着它所属的模块走：
材料相关的在材料清单模块里，官方渠道那几步在办理进展条上。
**已出结果的工单不显示「改派」。**

### 3.5.2 ① 办理进展条（4 段）

| 段 | 完成判定 | 显示内容 | 操作入口 |
|---|---|---|---|
| 1 收材料 | `st.ready` | 已齐备 / 尚缺 N 项 + 客户必交 X / Y | 看材料（锚到模块③） |
| 2 提交至官网 | `app_id` 有值 | 受理号 + 条形码 | 提交至官网 |
| 3 面签预约 | `appt_no` 有值 | 预约号 + 时间 + 地点；免面签产品显示「该产品免面签」 | 预约面签 / 改期 |
| 4 签证结果 | `visa_result` 有值**且不是 `ap`** | 结果标签 + 签证号 / 拒签归因 | 登记结果 |

**当前段** = 第一个未完成的段；之前的段标 ✓ 并高亮。
**已出结果（G3）的工单，进展条上不显示任何操作入口。**

> **行政审查（AP）不算走完**——它表示使领馆还没给结论，打上勾会让这一条看起来已经办结。
> 只有出签 / 拒签是终态。

**「此刻要做的」一句话**（跟在进展条下方）：

| 档位 | 文案 |
|---|---|
| G1 有缺项 | 等申请人补齐材料，还差 N 项。可在下面的材料清单里代客户上传，或把填写链接发给客户本人；逐项核对后点「通过」。 |
| G1 已齐 | 必交材料已全部通过，工单即将转入「处理中」。 |
| G2 未回填受理号 | 在官方渠道人工提交申请，再回填受理号。系统不代为提交。 |
| G2 未预约 | 在官方预约系统取号并与客户确认时间后登记，登记后客户在小程序上就能看到面签时间。 |

## 3.8 办理进展回填

**系统不代为提交。** 官方渠道无公开接口，提交、缴费、抢号、递交、采指纹五项均需人工操作，
系统只负责回填与留痕。按钮叫「提交至官网」，做的事是**回填**，弹窗里必须写清这层。

### 3.8.1 提交至官网 `/api/form/save`

| 字段 | 必填 | 说明 |
|---|---|---|
| 官网受理号（名称随国家变，如美签为 Application ID） | ✅ | 在官方渠道人工提交后拿到 |
| 条形码 / 副号 | — | 美签 DS-160 填十位条形码；其他国家可留空。**由 App ID 派生，不需另问客户或官网** |

回填后进度自动推进，众信与客户端同步可见。

### 3.8.2 预约面签 `/api/appt/save`

**弹窗提示**：「官方要「护照号 + 缴费收据编号 + 受理号」三样才放号，前两项没回填的这一步会被拦下。
登记后**客户在小程序上即可看到面签时间与地点**，门店销售也不必再来问。」

| 字段 | 必填 |
|---|---|
| 面签预约号 | ✅ |
| 面签时间（datetime） | ✅ |
| 面签地点 | — |

已登记后按钮变「面签改期」，弹窗标题同步变。

### 3.8.3 回填缴费 `/api/fee/save`（**无界面入口**）

## 3.9 签证结果登记

**接口** `/api/result/save` ｜ **权限** `uom`、`ubk`（`ubk` 校验归属 + gate）
**两端共用同一张表单** `woResultAsk()`。

### 3.9.1 表单字段（**按结果动态显示**）

| 字段 | 显示条件 | 必填 |
|---|---|---|
| 结果（出签 / 拒签） | 未勾选「行政审查」时 | ✅ |
| **尚未出结果，转行政审查（AP）**（勾选框） | 始终 | — |
| 签证号 | 结果 = 出签 且 未勾 AP | ✅ 校验：「出签须填写签证号」 |
| 签证有效期至 | 同上 | — |
| 单次停留天数 | 同上 | — |
| 拒签归因（7 选 1） | 结果 = 拒签 且 未勾 AP | ✅ 校验：「拒签须选择归因，退款金额依据该项计算」 |
| 拒签说明 | 同上 | — |

> 唐美芳 2026-09-08：「登记签证结果应该根据结果状态，动态展示下面的字段，
> 比如选中拒签结果，下面的拒签原因及说明才会展示。」
> **隐藏的字段不参与必填校验**（`ask()` 的 `showIf` 能力）。

### 3.9.2 为什么结果下拉里只有出签 / 拒签

> 唐美芳 2026-09-09：「签证结果只有出签和拒签 2 个终态，其他状态都属于中间态，不具备意义。」

- **行政审查是中间态**——它表示使领馆还没给结论。放在结果里会让列表出现一批
  「已出结果但查不到结果」的单。现在它挪到勾选框，**进度停在「待出结果」**，
  记 `ap_due = 今天 + 15 天`，15 天后提醒复查。
- **撤签是客户单方撤回**，属于订单侧的取消 / 退款，不是使领馆给的结果。
- 历史数据里已有的 `ap` / `withdraw` 仍能正常展示，只是不再新增。

### 3.9.3 写库与副作用

| 分支 | 写库 | 进度 |
|---|---|---|
| 勾了 AP | `visa_result='ap'`，`ap_due=+15d` | 推到 P5（若当前 < P5），**不算办结** |
| 出签 / 拒签 | 结果 + 签证号 / 有效期 / 停留 / 拒签归因 / 拒签说明，清空 `ap_due` | **推到 P6 已完成**（跳跃时自动补齐中间节点） |

Toast：AP 分支「已转行政审查，请于 YYYY-MM-DD 前复查后再登记结果」；正常分支「结果已登记」。

### 3.9.4 责任判定 `/api/liability/set`

**权限** `uom`、`lead`（供应商无权判定）。拒签后判定责任方（我司 / 客户 / 使领馆 / 未判定），
返回退款口径提示，供退款链路计算金额。

## 3.11 进度状态机完整流转

| 从 | 到 | 触发 | 谁 | 前置校验 |
