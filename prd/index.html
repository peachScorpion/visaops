0.1 这份文档是干什么用的

这是技术层需求文档，写给三类人看：

  • 唐美芳（验收方）——按册逐页对照系统，检查按钮、状态、字段、文案是不是对的；
  • 开发（实现方）——照着建表、写接口、做页面，不需要再回来问"这个按钮点了以后什么状态"；
  • 测试（验证方）——每条状态流转、每个按钮的可见条件都写了前置条件与结果，可以直接转成用例。

文档口径以线上跑着的系统为准。 全部接口清单、页面清单、数据字典由 tools/prd_extract.py 从 server/app.py 与 visaops.db 直接抽取，不是手写的，因此不会出现"文档写了系统没有" 或"系统改了文档没跟"。正文（第 0–4 册）是人工撰写的业务口径与交互规则。

怎么用它验收：每一页都按同一套骨架写—— 页面入口 → 谁能进 → 列表字段 / 页签 / 筛选 → 每个按钮（名称·可见条件·点击后发生什么·二次确认文案）→ 状态定义与流转 → 字段校验。 验收时对着"按钮"和"状态流转"两节看，发现和系统不一致的直接标出来，改代码或改文档。

0.2 系统定位与业务边界

VisaOps 把众信的签证业务从"全人工"搬进系统，覆盖从供应商上品到客户拿到签证结果的完整链路。

业务模型：自营 + 供应商双轨

  • 产品来源：产品由供应商在 UBK 自行录入并报价，平台目录随之自动登记。平台侧（OPS）

只管材料标准（签证表模板 / 材料样例 / 国家送签材料库）与审核放行，不建产品、不定价。

  • 履约主体：签证办理中心以供应商（UBK）为主力，众信侧（UOM）看整体节奏并协助操作。

> 唐美芳 2026-09-08：「签证办理中心现在主要就是 UBK 干活，UOM 只是查看整体节奏和协助操作。」

  • 双通道销售：B 端（CSP 门店 / 同业）与 C 端（客户小程序）分别审核、分别上架。

供应商上品默认上架 B 端；勾选「上架 C 端」才会同时出现在客户小程序。 > 唐美芳 2026-09-09：「B 只审核 B 的，C 只审核 C 的，2 拨人处理，所以千万不要混在一起。」

硬约束：五项动作永久保留人工

各国官方签证系统（CEAC / VFS Global / TLScontact / ustraveldocs）均无公开 API、且不授权第三方抓取。 以下五项对外不得承诺自动化，系统只做辅助（预填、提醒、留痕），不做代操作：

#动作系统能做的系统不做的

2签证费缴纳记录缴费金额与回执号代客在官网付款
3面签号抢占记录预约号与时间地点、到期提醒自动刷号

5生物信息采集（指纹）提示需采集、记录采集点任何形式的代办

本期不做

  • 分销分润与返佣（唐美芳明确口径：本期不涉及）；
  • 原件寄回给客户由签证中心 / 银行直接寄回客户本人，不经供应商，因此无「资料返还」履约环节。

> 唐美芳 2026-09-09：「一般原件寄回不需要经过供应商，签证中心会通过银行或者直接寄回的方式，所以寄回功能不需要。」

0.4 核心对象与引用链

理解这两条链，系统的大部分"为什么这里查不到数据"就能自己回答。

链一：材料标准（配置侧，自上而下）

国家签证表模板 formver   ← 底层字典，一个国家一套官方表（如 日本 · 签证申请书）
        ↑ formver_id
国家送签材料库 fullver   ← 某国某签证类型的完整送签清单，一个版本一份
        ↑ fullver_id       （含 fullver_item：逐项材料，分人群、分提供方式）
       产品 product / 供应商产品 sup_product

关键规则（2026-09-09 修正）：

  1. 表模板是底层字典，可被多份材料清单反复引用，因此它**只有「启用 / 禁用」两个状态，

没有发布状态。国家送签材料库只能引用处于启用状态的表模板**。 > 唐美芳原话：「这个模板是底层，可以被国家送签材料库多次引用，所以国家签证表模板只需要有启用、禁用…… > 你现在加上了发布未发布状态整复杂了，退回下。」

  1. 工单要填哪张官方申请表，沿引用链取，不按国家猜：

订单 → 供应商产品（优先）/ 平台产品 → fullver_id → fullver.formver_id → formver。 任一环断裂，工单上的「填申请表」按钮置灰并提示断在哪一环，不再报笼统的"模板不存在"。

  1. 材料项数对不上是正常的，两者口径不同：
  2. 国家送签材料库的项数 = 该国送签要交的全部材料（含护照、照片、在职证明、银行流水…），

其中一部分由客户提供，一部分是我方凭证；

  • 国家签证表模板的项数 = 官方申请表上的题目数（客户必填题 / 选填题）。

一个是"要交几样东西"，一个是"表上要答几道题"，不应相等。

链二：交易与履约（运行侧，自左而右）

订单 ord ──┬── 办签人 applicant（一单多人）──── 工单 wo（一人一单，1:1）
           │        ├── 材料 mat（逐项，可驳回）
           │        └── 官方申请表任务 form_task ── 答案 form_answer
           ├── 收款 pay / 应付 payable / 退款 refund
           └── gate（财务收款放行开关：0 未放行 / 1 已放行）

关键规则：

  1. 一个办签人一张工单（wo.applicant_id 唯一），工单号 VW- 开头，全局唯一可搜。

订单号 VS- 开头。同一订单多人，就是多张工单，可分派给不同经办人。

  1. 收款放行 gate 是履约的总闸：ord.gate = 0 时供应商看不到工单、任何履约动作被拒。

财务在收款管理确认到账后置 gate = 1。 > 唐美芳 2026-09-08：「必须财务点确认到账后才能开始干活。」

  1. 办签人资料必须在支付前录齐：下单后 24 小时内未录齐 → 订单自动取消（ord.info_deadline）。
  2. 订单状态只管钱走到哪（5 个值），办理进展是由办签人进度聚合出来的派生值，不落在订单状态上。
